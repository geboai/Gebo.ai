# Internal knowledge base search policy

## 1. Understand the search command

Before searching, identify:

* The exact topic, entity, document, concept, or fact being requested.
* Whether the request asks for:

  * direct factual retrieval;
  * document discovery;
  * evidence ranking;
  * contradiction detection;
  * historical comparison;
  * technical explanation;
  * implementation details;
  * source validation;
  * missing information analysis.
* Any explicit filters:

  * project;
  * knowledge base;
  * date range;
  * document type;
  * author;
  * customer;
  * system/module;
  * language;
  * version;
  * technology;
  * security/access constraints.
* Any implicit aliases, synonyms, acronyms, legacy names, or renamed components.

If the command is ambiguous, perform the best reasonable search using the shared context and return the ambiguity in your result.
Do not block the workflow with clarification unless the search would be meaningless.

## 2. Search behavior

Search the internal knowledge base using the most effective strategy available.

Prefer a layered search strategy:

1. Exact search for explicit names, identifiers, document titles, file names, codes, APIs, classes, tables, modules, or quoted phrases.
2. Semantic search for conceptually related passages.
3. Alias/synonym search for alternate names and historical names.
4. Narrowed search using metadata filters when available.
5. Broader recall search if exact search produces weak or no results.

When useful, search for both:

* positive evidence supporting the requested claim;
* negative or contradictory evidence disproving or limiting the claim.

Avoid returning generic chunks that only weakly match the query.

## 3. Evidence quality rules

For each retrieved evidence item, evaluate:

* Relevance to the command.
* Source authority.
* Freshness.
* Specificity.
* Completeness.
* Whether it directly answers the question.
* Whether it is primary evidence or secondary interpretation.
* Whether it conflicts with other evidence.
* Whether the passage is self-contained enough to be useful.

Prefer evidence in this order:

1. Exact internal documents, specifications, contracts, source code, logs, tickets, or official records.
2. Recent maintained documentation.
3. Explicit decisions, meeting notes, architectural documents, or implementation notes.
4. Older but still applicable documents.
5. Indirect references or partial mentions.
