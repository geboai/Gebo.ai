Architecture Decision Record · Draft for review

Bringing A2A to the Gebo agent network

A plan to export Gebo agents & agent-networks over the Agent2Agent protocol, and to register external A2A agents as first-class network participants — persisted in Mongo, built entirely on patterns the codebase already uses.

gebo.architecture.parent 2 new modules 0 core-contract changes precedent: mcp-server / mcp-clients 2026-08-28

The agent layer is already a network-of-agents runtime with a native capability model and a live streaming lifecycle. A2A is the same shape of problem the MCP modules already solve — export internal capability, integrate external capability — over a different wire format. This plan reuses those two precedents almost line-for-line.

Decisions locked · 2026-08-28

Protocol: official A2A Java SDK (not hand-rolled) — exact artifact/version & Spring-MVC fit confirmed before coding.  Task lifecycle: SSE-first (synchronous + message/stream).  Layout: a2a-server / a2a-clients.

Scope: both directions, secure by default — no agent and no network of agents is externally visible or callable unless an admin has explicitly configured and enabled it. enabled defaults off on both sides; ACLs still gate callers.

The thesis

IGGenericAgentService.getAgentCapabilities() is already an “agent card” in all but wire format; IGNetworkAgentService.onMessage() + the reactive Flux/Sinks path is already a task lifecycle; and IGDynamicAgentServiceSupplier is a clean seam for injecting remote agents at runtime. A2A needs a projection of these onto JSON-RPC + Agent Cards, not new agent machinery.

PART 1

What already exists

Grounding, with the real types the plan builds on.

The agent runtime — gebo.architecture.agents.abstraction.layer

  • Capability model. IGGenericAgentService.getAgentCapabilities(GAgentConfig) returns AgentCapabilities — a summary plus lists of capabilities, catalogs, resources, tools, each an AgentCapabilityResource{code, name, description}. Its own Javadoc says it’s rendered into “the shared network-of-agents description used by coordinating agents to reason about their reachable peers.”
  • Network agent contract. IGNetworkAgentService<I,O> handles an AgentsExchangeMessage<I> and returns List<AgentsExchangeMessage<O>>, driven inside a GAgentsNetwork (participants, CommunicationPolicy ALLOW/DENY lists, input/output nodes, maxLoopIteration). Progress streams through INotificationSink; the reactive variant emits IGPartialOperation<O> onto a Flux via Sinks.Many.
  • Runtime aggregation. AgentServiceRuntimeDaoImpl gathers every IGGenericAgentService bean plus every IGDynamicAgentServiceSupplier.get(). That supplier is how the standard module already injects runtime agents (e.g. externalSourcesAgentServicesSupplier()).
  • Persistence & CRUD. GAgentConfig / GAgentsNetwork extend GBaseObject (Mongo @Id code), stored via IGBaseMongoDBRepository<T>, surfaced through IGRuntimeConfigurationDao, mutated through an IGAgentsNetworkCrudService returning OperationStatus<T> + GUserMessages, all ACL-secured via IGObjectWithSecurity/IAclGrantedResource (accessibleToAll/Users/Groups, aclAliases).

Chat — gebo.architecture.chat.abstraction.layer

A pipeline/step engine (routing, RAG, tool-using, deep-search steps) with reactive streaming output (ISinkUIEmitter) and Mongo-persisted session state. It consumes the agent network through gebo.architecture.agents.standard — GReactiveChatAgentsNetworkService extends GAbstractReactiveOutputAgentsNetworkService<ChatPipelineExecutionRuntimeData, GeboChatMessageEnvelope> and exposes getFlux(). A2A doesn’t touch chat directly; it plugs in one layer below, at the agent runtime.

Part 3.1 — Exporting a whole network-of-agents as ONE A2A agent

The primary export unit: a network presented as a single agent with its own input/output. A2A agents are opaque services — a caller sees a card and a task interface, never the internals — and a Gebo network maps to exactly that: one card, one endpoint, the member agents / routing / loop iterations hidden behind it.

Wiring status — verified against the code (correction)

The runtime execution layer for “a network as one unit” exists and is exercised; the AgentType.AGENTS_NETWORK config indirection is declared but NOT wired. Do not treat it as production-ready.

Proven (chat runs on it): IGAgentsNetworkService<I,O> (executeNetwork(...), getInputType/getOutputType; reactive getFlux() for message/stream) built by IGAgentsNetworkServiceFactory / GReactiveChatAgentsNetworkServiceFactoryImpl (ChatPipelineExecutionRuntimeData → GeboChatMessageEnvelope).

Declared but unwired (verified): nothing branches on agentType (getAgentType() never read); no code ever sets adaptedAgentNetworkCode/agentNetworkServiceCode (only read inside the adapter); and the one registered adapter bean (GStringToStringAgentsNetworkToNetworkAgentAdapterServiceImpl, String→String) has no compatible factory — the sole factory is chat-typed, whose input is not assignable from String. No text/parts network factory exists.

Consequence — call the proven path, not the AGENTS_NETWORK indirection. A2ATaskBridge resolves an exported network via IGAgentsNetworkServiceFactory.create(network, sink, inputType, outputType, runAs) then executeNetwork(...) / getFlux() — the same path chat uses. The adapter + AGENTS_NETWORK config machinery is an unfinished convenience: bypass it (recommended), or finish-and-test it as explicitly scoped work.

Both export kinds unify on ONE path — a single agent is not independently runnable

Verified: an agent’s only execution entry points — IGNetworkAgentService.onMessage(...) and IGReactiveAgentService.execute(...) — both require full network context (GAgentsNetwork, the AgentNetworkParticipant persona, an AgentsCollaborationSessionContext, private memory, the runtime DAO), and the only caller anywhere is the network executor. IGGenericAgentService has no execution method. There is no “just call an agent.”

So A2ATaskBridge runs both kinds through executeNetwork(): NETWORK → the referenced network; AGENT → a synthesized ephemeral single-node GAgentsNetwork whose one participant (the exported GAgentConfig) is both input and output node. Per-kind difference is only card construction + the trivial one-node synthesis.

Provenance — static or code-generated, addressed uniformly. A GAgentsNetwork can be persisted in Mongo (AgentsNetworkRepository) or generated purely in code (an IDynamicAgentsNetworkDataSource, e.g. the default streaming chat network). AgentNetworkConfigDaoImpl composes both (code-generated ones cloned, readOnly=true) and findByCode(code) resolves across both — so an export references a network by code regardless of provenance, and the factory is already named on GAgentsNetwork.agentsNetworkServiceFactoryId.

I/O type is a consequence of the node agent services. executeNetwork() validates input against the input-node participant’s service (inputRuntime.getService().getInputType().isAssignableFrom(input.getClass())); output flows from the participants’ output types. So the card’s advertised I/O and the marshalling derive from the input/output node agent service ids and their types — a network is text/parts-exportable only if its input node accepts a marshallable type. The default chat network’s input node adapts ChatPipelineExecutionRuntimeData (not text), which is exactly why a generic text export needs marshalling / a text-in node.

New work this exposes

Exporting an arbitrary network with A2A text/parts I/O needs a network-service factory (and input/output node services) whose I/O is A2A-friendly (e.g. String → String, or a parts-aware type). Only the chat-typed factory exists today — so this factory, plus the I/O marshalling between A2A Parts and the network’s typed I/O, is genuinely new, not reuse.

The card for a network: name ← network code; description ← GAgentsNetwork.scenarioDescription; a single skill whose I/O modes come from the network service’s getInputType()/getOutputType(). Optional, default off: exposeMemberCapabilities aggregates each participant’s getAgentCapabilities() into the skill for richer discovery; default keeps it opaque, which also reinforces secure-by-default (member agents never individually reachable).

PART 5

Shared wire model

Decision: use the official A2A Java SDK rather than hand-rolling POJOs. The SDK supplies the wire vocabulary (AgentCard, AgentSkill, capabilities, security schemes; Message+Part; Task, TaskStatus, TaskState, Artifact; JSON-RPC envelopes) and the dispatch, so both sides stay spec-conformant by construction. Gebo-side work: map AgentCapabilities ↔ the SDK’s AgentCard, and bridge the SDK’s task handler ↔ IGNetworkAgentService / the streaming lifecycle.

Open sub-question — needs confirmation before coding

Exact SDK artifact + version, and its transport fit. The canonical impl is a2a-java (io.a2a.sdk:*), not yet in the local .m2, and its server transports are Jakarta/Quarkus-oriented — while this repo serves MCP over Spring MVC RouterFunctions with a hot-reload registry. The client side can use the SDK client cleanly; the server side needs verification that a Spring-MVC-compatible server transport exists (or that we drive the SDK request handler from our own RouterFunction). Fallback: use the SDK types for the wire model, keep our own Spring MVC JSON-RPC/SSE handlers. I’ll confirm against Maven Central first.

PART 6.1

Identity, credentials & impersonation

Identity semantics differ by direction — and this is where A2A needs something the MCP server did not. The MCP server reuses the local Spring Security principal (GeboMcpSecurityContextSupport captures the authenticated Authentication and re-establishes it so handlers run “under the identity of the calling (impersonated) user and honour that user’s ACLs”; GeboMcpAccessChecker checks isCanDo(config, READ, EXECUTE)). That works because MCP callers are local. An A2A caller is external.

Outbound — coherence is authMode-dependent, not blanket impersonation
SERVICE MODES
API_KEY · BEARER · CLIENT_CREDENTIALS
Remote sees Gebo-as-a-service. Local user NOT propagated; credential NOT mapped into local Spring Security. Local ACLs still gate who may invoke.
PER-USER MODES
AUTH_CODE_PER_USER · TOKEN_RELAY · TOKEN_EXCHANGE
Local user’s own/exchanged token relayed → remote sees the actual local user. Coherent — but this is delegation, not impersonation.

RemoteA2ANetworkAgentService runs locally as a network participant under the local invoking user’s runAs, and presents outward whatever authMode dictates. No automatic impersonation of remote agents.

Inbound — impersonation MUST be coherent with a local principal (decided)

The exported network runs via executeNetwork(... runAs ...) against a local Spring Security principal. Requirement: the inbound credential must itself resolve to a local principal, and the network impersonates that principal — never a synthetic identity divorced from a real Gebo user. This reuses existing auth, not new machinery:

Gebo-generated API key is already a JWT bound to a local user — GGeneratedApiKeyServiceImpl sets impersonatedUser and mints it via jwtTokenProvider.createToken(username, …); presented as an inbound bearer it resolves to that user through the normal JWT chain. OAuth2 tokens federate to a local user the same way; any other auth that establishes a local principal is treated identically.

So the a2a-server endpoint sits behind the same Spring Security chain as the rest of the product — itself deployment-configurable: Gebo runs with its own JWT / API-key mechanism (LocalJwtTokenProvider) or as an OAuth2 resource server (GeboSecurityConfig.oauth2ResourceServerEnabled, default true; per-issuer JwtDecoderCache via GHttpRequestAuthenticationManagerResolverImpl). The a2a-server implements no auth of its own: whichever mode is active validates the bearer token and yields the local Authentication; the bridge runs the network runAs that principal, honouring that user’s ACLs (ReactiveIdentityUtil + IGSecurityService.isCanDo). The AgentCard’s securityScheme mirrors the active mode. A credential that resolves to no local principal is rejected (401) — never run under a fallback identity.

PART 8

Build order

A genuine sequence — each step compiles and is testable before the next.

  1. Shared wire model (a2a-common)
    AgentCard, Skill, Message/Part, Task/TaskStatus, JSON-RPC envelopes. No dependencies; unit-testable against sample A2A payloads.
  2. Module B — a2a-clients
    Config + repo + connector + testAndDiscovery + RemoteA2ANetworkAgentService + supplier + controller. Lands remote agents in the network composer first — the higher-value half.
  3. Module A — a2a-server
    Config + repo + card builder + registry + dispatcher + builder + task bridge + manager + controller.
  4. Wire into the build
    Register both modules in gebo.architecture.parent/pom.xml and the monolith starter (and brain.gebo.ai if agents run there), following the mcp modules’ dependency sets.
  5. Angular admin UI
    Two admin screens mirroring the existing MCP client/server screens. Follow-on.
